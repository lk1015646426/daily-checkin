# TRAE 官方设备身份对齐设计

## 目标

让切换工具的本地签到与 GitHub Actions 云签到按 TRAE Work 官方客户端的请求语义发送设备身份，并让凭证刷新区分“Token 轮换”和“设备身份修复”两类场景。

## 已确认事实

- 官方客户端签到请求的 `x-device-id` 来自设备注册服务的 `guaranteedDeviceId`，对应账号快照中的数字型 `auth_device_id`。
- 现有切换工具和云签到把 UUID 型 `telemetry.devDeviceId`（`checkin_device_id`）作为 `x-device-id`。
- 同一账号在官方客户端返回 `9095`“当前设备今日已经签到”，在直连代码中返回 `9074`“操作太过频繁”，说明请求设备身份未对齐。
- 官方客户端还按可用性附加 `x-device-brand` 与 `x-device-type`。
- 当前刷新流程只要 Token 剩余时间超过 5 天就判定成功，即使 Token 内容和签发时间没有变化。

## 方案比较

### 方案 A：完整对齐官方请求并按凭证状态分流（采用）

本地和云端统一使用 `auth_device_id`，补齐官方设备头。刷新流程先验证目标账号 UID、有效 Token、数字设备 ID 和同一设备密钥；仅当 Token 过期或即将过期时等待官方客户端轮换 Token，Token 仍有效但设备身份需要修复时直接同步。此方案保留账号安全边界，同时不把服务端没有要求的 Token 轮换误当成设备同步前提。

### 方案 B：只替换设备 ID

改动最小，但仍保留与官方不同的设备头和刷新误报，若服务端继续校验请求上下文，仍可能返回 `9074`。

### 方案 C：让官方客户端代为签到

本地可行但无法用于无桌面会话的 GitHub Actions，也会把自动签到绑定到正在运行的 GUI，不满足云签到目标。

## 设计

### 设备身份解析

- 新增纯函数，从 `TraeAccount` 解析官方签到设备 ID。
- 只接受非空的数字型 `auth_device_id`；不再把 UUID 型 `checkin_device_id` 静默当作官方签到 ID。
- 缺少官方设备 ID 时返回明确错误，提示重新导入当前官方客户端账号快照。
- `checkin_device_id` 保留在账号模型中，继续服务于原有快照兼容场景，但不再用于签到请求。

### 本地签到

- `Authorization` 保持 `Cloud-IDE-JWT <token>`。
- `x-device-id` 改为官方数字设备 ID。
- 补充 `x-device-brand` 与 `x-device-type`；值复用现有 TRAE 登录上下文检测逻辑，优先从官方日志读取设备型号，系统类型在 Windows 上为 `windows`。
- 删除人为添加的 `Origin`、`Referer` 和自定义 `Trae/1.0.0` User-Agent，使显式请求头与官方实现一致；底层 HTTP 库仍可发送自己的标准 User-Agent。
- 不增加自动重试，避免业务失败后重复领取。

### GitHub Secrets 与云签到

- 继续复用现有 `<SLOT>_DEVICE_ID` Secret 名称，避免用户重新配置工作流。
- 切换工具同步该 Secret 时改写为 `auth_device_id`，同时新增 `<SLOT>_DEVICE_BRAND` 与 `<SLOT>_DEVICE_TYPE`。
- 云签到配置为每个 TRAE 账号读取三项设备 Secret，并仅在非空时发送品牌和类型头。
- 缺少数字设备 ID 时该账号失败并给出配置错误，不回退 UUID。

### 刷新凭证

- 流程开始时记录目标账号 UID、Token 元数据和当前设备快照。
- 切换后必须确认当前客户端 UID 与目标账号一致，并读取非空、未过期的 Token、数字 `auth_device_id` 以及匹配的设备密钥；临时半套快照不得覆盖已有完整设备上下文。
- 若 Token 已过期或在刷新窗口内即将过期，继续等待匹配账号的 `TOKEN_UPDATED` 事件或 Token 元数据变化；超时报告 Token 轮换失败。
- 若 Token 仍有效且设备快照完整，即使 `iat/exp` 未变化也允许进入 GitHub 同步；这是设备身份修复路径，不宣称发生了 Token 轮换。
- “Token 还剩 5 天以上”只用于判断是否需要轮换，不再作为凭证刷新成功的唯一条件。

### 诊断与错误处理

- 本地签到结果继续显示 HTTP 状态、业务码和阶段。
- 诊断只显示设备 ID 类型（numeric/missing）与设备头是否存在，不记录 Token 或完整设备 ID。
- `9095` 保留原始服务端文案，作为设备当日已签到；`9074` 仍按业务失败展示，不自动重试。

## 测试

- Rust 单元测试：数字 `auth_device_id` 被选中；UUID 不被误用；缺失时报错；GitHub Secret 同步使用官方 ID 并写入品牌/类型。
- TypeScript 单元测试：过期 Token 未变化时刷新不能同步；有效 Token 未变化但设备快照完整时允许同步；Token 变化或收到匹配更新事件时快速同步；缺少 UID、数字设备 ID 或密钥时拒绝同步。
- Python 单元测试：云端请求读取并发送官方设备头；缺少可选品牌/类型时不发送空头；设备 ID 必填。
- 回归测试：两个项目现有测试全部通过，切换工具 Release 构建成功。
- 在线最小验证：已签到账号改后应从直连 `9074` 变为与官方一致的 `9095`；真正领取留到次日未签到账号验证，避免重复请求。

## 范围限制

- 不伪造官方 TLS/TTNet 指纹。
- 不绕过服务端设备每日限制或新账号规则。
- 不增加并发、重试或多账号轮询。
- 不输出、提交或记录任何 Token 与完整设备标识。
